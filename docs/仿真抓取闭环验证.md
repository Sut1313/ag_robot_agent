# Agent 仿真抓取闭环验证（2026-10-29）

## 已验证的闭环

在独立 ROS 域和 Gazebo 分区中，`piper_with_yolo_graspnet` 后端完成了：

1. Agent 自动启动 Gazebo Harmonic、YOLO 桥接和 GraspNet 容器；
2. YOLO 从仿真 RGB-D 识别 `cylinder`，GraspNet 生成 6D 抓取候选；
3. MoveIt 对 approach、grasp、lift、place 四阶段彩排通过，Agent 签发一次性令牌；
4. 仿真正式执行抓取、转运、放置和回零；
5. `pick_state.json` 最终为 `phase=complete`、`placed=["cylinder"]`、`pending=[]`；
6. Agent 退出时停止自身启动的仿真和容器，无残留进程。

默认配置实测域 `ROS_DOMAIN_ID=62`、`GZ_PARTITION=yolo62`。彩排的第一帧有 24 个候选，正式执行第二帧有 8 个候选；两次四阶段规划均通过。正式执行日志包含 `cylinder grasped, transferred, and placed` 和 `task complete: placed=1/1 dry_run=false`。

另在域 `64/yolo64` 通过自然语言让 ROSA 调用 `yolo_pick`：`job_1` 彩排成功并签发令牌，`job_2` 正式执行成功，最终状态同样为 `placed=["cylinder"]`、`pending=[]`。原始模型曾在最后一次口头汇报中沿用旧彩排结果；CLI 的任务状态查询现直接读取工具结果。

## 复现

```bash
source /opt/ros/humble/setup.bash
source .venv/bin/activate
export ROS_DOMAIN_ID=65 GZ_PARTITION=yolo65
python agent.py --mode sim --profile grasp --auto-confirm-sim
```

在同一个 Agent 会话中依次提出：

1. “在仿真中对 cylinder 做抓取彩排。”
2. 等待任务结束，使用 `yolo_pick_status(job_id)` 确认 `result.success=true` 和 `result.token_issued=true`。
3. “仿真工作区已确认安全，执行 cylinder 抓取。”
4. 等待任务结束，再查状态，确认 `result.success=true`、`pick_state.placed=["cylinder"]`。

`yolo_pick(dry_run=true)` **会移动机械臂**到观察和规划姿态，只是不夹取物体。正式执行需要同一会话内的成功彩排、未过期且候选文件未变的令牌；仿真可用 `--auto-confirm-sim` 跳过键盘确认。真机不允许使用该后端。

现在桥接节点在空闲时每秒写入 `detections_live.json` 和 `yolo_overlay_live.png`。这些文件只供 Agent 查询和识别窗口显示，不创建 `.ready`，不会触发 GraspNet。抓取请求仍按原有 `pick_state` 版本提交一次 RGB-D 帧，执行器仍按候选时间戳拒绝旧抓取数据。Agent 根据当前 ROS 图中的 `yolo_bridge_node` 选择后端 B，超过 10 秒的检测帧返回过期错误，不再冒充实时检测。

## 2026-10-29 现场故障：急停后的彩排

16:01 的 `estop` 成功停用了 `arm_controller` 与 `gripper_controller`。16:04 的 cylinder 彩排和 16:09 的 cube 彩排没有先 `recover`：MoveIt 的初始回位轨迹被停用的 `arm_controller` 拒绝，执行器以代码 4 退出，`pick_state` 停在 `initializing`，并未进入感知。此前 Agent 只等待 launch 父进程结束；MoveIt 子进程仍在，造成表面上的“卡住”。

`yolo_pick` 现先检查两个控制器均为 active；若急停后仍停用，会立即返回需运行 `recover` 的错误。任务监控也会识别执行器提前退出并返回具体错误，不再等待 300 秒超时。现场验证在控制器 inactive 时，新的工具调用立即返回失败，且不会启动抓取执行器。恢复控制器仍由 `recover` 工具要求用户确认。
